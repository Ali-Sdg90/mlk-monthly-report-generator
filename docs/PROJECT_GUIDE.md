# Project Guide

## Overview

MLK Monthly Report Generator is an internal browser application that turns two monthly housing-market workbooks into a fixed A4 RTL report. It validates and normalizes the data, calculates period changes, renders a preview, and opens the browser print dialog for PDF export.

The project uses React, Vite, JavaScript, SCSS, and `read-excel-file`. It has no backend or database.

## Application flow

```text
Select XLSX files
  -> validate workbooks
  -> parse and normalize rows
  -> calculate report data
  -> render preview
  -> print or save as PDF
```

The main files in this flow are:

- `useReportUploads.js`: file and validation state
- `workbookValidation.js`: workbook rules and validation results
- `workbookParser.js`: normalized workbook data
- `createReportData.js`: calculations and final report model
- `ReportDocument.jsx`: report page order and rendering
- `printReport.js`: font/image readiness and browser printing

## Workbook contract

Both inputs must be `.xlsx` workbooks containing exactly two sheets:

1. Current period
2. Previous comparison period

Sheet names must contain a supported Persian or Latin month and one Solar Hijri year, such as `مرداد 1404` or `Mordad1404`. The two workbooks must represent the same periods.

### All Cities workbook

| Field          | Required header    |
| -------------- | ------------------ |
| Location       | `City`             |
| Sale price     | `Sale Sqm Price`   |
| Mortgage price | `Mortg. Sqm Price` |
| Ratio          | `Ratio (Average)`  |

Each period must contain one row for Tehran, Karaj, Mashhad or Khorasan, Shiraz, Isfahan, and Northern Cities.

### All Cities Zones workbook

| Field          | Required header             |
| -------------- | --------------------------- |
| Province group | `CityTitle`                 |
| Region         | `CityZone`                  |
| Sale price     | `SellSqmPriceAvg (Average)` |
| Mortgage price | `MortgageSqmAvg (Average)`  |
| Ratio          | `Ratio (Average)`           |

Each period must contain rows for Tehran, Karaj, Khorasan or Mashhad, Shiraz, Isfahan, and Northern Cities.

Prices may be numbers, numeric strings, grouped values, or values such as `59M` and `59 میلیون`. Ratios may be decimals such as `0.18` or percentages such as `18%`. Persian and Arabic digits are normalized before parsing.

Workbook definitions are centralized in `src/features/report-upload/config/workbookRequirements.js`.

## Calculations

Price changes use percentage growth:

```text
((current - previous) / previous) * 100
```

Ratio changes use percentage-point difference:

```text
(currentRatio - previousRatio) * 100
```

Calculations live in `reportCalculations.js`. Parsed values remain numeric; display formatting belongs to report components.

## Report structure

The report currently contains eight pages:

1. Cover
2. All Cities summary
3. Tehran
4. Karaj
5. Mashhad
6. Shiraz
7. Isfahan
8. Northern Cities

Pages 3 through 8 reuse `ReportPage03.jsx` with region-specific data and maps. Districts are sorted numerically, followed by other region names sorted with the Persian locale.

Report pages are real React/HTML/SCSS content, not design images. They use fixed A4 measurements and page breaks. Browser preview scaling must not change the print layout. `Design/pages/` is the visual reference for the original page designs.

## Project structure

```text
src/
  app/                         application root
  components/layout/           shared application layout
  features/report-upload/      validation and parsing
  features/report-workflow/    upload-to-preview flow
  features/report-preview/     report data, pages, assets, and printing
  styles/                       shared application styles
Design/files/                  example workbooks
Design/pages/                  report references
public/                        public branding and metadata
```

Keep validation, parsing, calculations, report-data creation, rendering, and printing separate. Prefer existing utilities and components, and avoid unnecessary dependencies or generic abstractions. Never edit `dist/`; it is generated by Vite.

## Development and verification

```bash
npm ci
npm run dev
npm run check
```

Use the checks appropriate to the change:

- Workbook changes: test valid and invalid files and inspect parsed values.
- Calculation changes: recompute representative values independently.
- UI changes: test the real browser interaction.
- Report changes: compare the rendered page with `Design/pages/`.
- Print changes: inspect page count, A4 size, page breaks, clipping, fonts, and images in the saved PDF.

Formatting, linting, and building do not prove correct workbook behavior or visual/PDF quality. Record each type of verification separately.

## Release

Pushes to `main` run formatting, linting, and build checks. Semantic-release then creates the version and GitHub release, and the workflow deploys `dist/` to GitHub Pages. Production uses the Vite base path `/mlk-monthly-report-generator/`.

Use Conventional Commits: `fix` for patch releases, `feat` for minor releases, and breaking changes for major releases.

## Known limitations

- Zone validation does not currently reject duplicate `(province, region)` rows.
- Zone validation does not require identical region coverage across both periods.
- Browser upload behavior and final PDF layout still require manual verification.
